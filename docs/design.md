Источник — разговор пользователя с лидом 24–25.10 (транскрипт лида `~/.claude/projects/-home-alice/0bbcc980-299c-4952-9456-a5d0841affb0.jsonl`) и страница «Набор инструментов для агентов» (https://claude.ai/artifact/HPRg6uPQfYNPK1acqvkkQj, раздел «Страж»). ## Зачем
Пользователь 25.10: «это должен быть один демон который следит за всеми агентами… в виде демона будет удобнее следить за длительными процессами контроля памяти, винта и т.п.»; «это должен быть контроль за всеми ресурсами потребляемыми агентом, за границами его действий. И тут я под контролем имею в виду не только то, чтобы агенты не выжирали весь винт или оперативу, а чтобы страж следил, что этих и других ресурсов в принципе достаточно».

Имя: a = agentic, проект только для агентов, как akit (схема — `~/git/akit/docs/design.md`, «Имена и репозиторий»).

## Три слоя
- **Хуки (chooks)** срабатывают на конкретный шаг агента: перед командой, в конце хода, при отправке реплики. Видят одну сессию в один момент и должны отвечать мгновенно.
- **aguard** — один постоянный демон. Видит все сессии и всю машину сразу, следит за тем, что тянется долго. Сам в ход агента не вмешивается: агенту приходит сообщение.
- **cl** (`cmd/cl` этого репо, бинарь `~/bin/cl`) — тонкий запуск: флаги, имя сессии, `agents.slice`, перезапуск и сжатие в том же терминале. Перезапустить сессию может только её родитель, а родитель — cl. Решение «пора ли перезапускать и сжимать» (сессия простаивает, нет фоновых задач и невосстановимых таймеров, версия старее) — наблюдение за сессией, его принимает aguard; cl спрашивает «можно?» и исполняет. cl жил отдельным репо `~/git/cl` (на GitHub `aiseeq/cl`, в архиве); перенесён в aguard, чтобы логика жила в одном месте: предложение лида, пользователь 25.10 18:33 CET: «Да, согласен со всем, делай» (транскрипт лида `~/.claude/projects/-home-alice/0bbcc980-299c-4952-9456-a5d0841affb0.jsonl`).

## Что входит
| что | сейчас | в aguard |
|---|---|---|
| процессы-сироты умерших сессий | procguard (исходники `~/.local/share/tmpguard`, режим observe) | то же |
| мусор в `/tmp` (это оперативка) и чей он | tmpguard | то же |
| можно ли перезапустить сессию | решение cl | решение здесь, перезапуск — в cl |
| недельные лимиты учёток и переключение | chooks `account rotate`, запускается строкой статуса, то есть только пока она рисуется | постоянное наблюдение и прогноз; строка статуса только показывает |
| «машина занята, подожди» | три копии: graft (`loadgate`, `workers`), `when-idle.sh`, tmpguard | одно правило в библиотеке akit, aguard его применяет |
| снимки «кто съел память» | системный таймер `mem-pressure-snapshot` | то же |
| последняя защита от нехватки памяти | earlyoom | earlyoom остаётся: он должен работать, даже если aguard упал |

Из chooks уходит только переключение учёток с прогнозом (решение лида 25.10). Уведомления, `skill_reload`, `jira_style`, проверка вопросов и строка статуса — реакции на шаг агента, остаются хуками. Правка chooks при переносе — только с «да» пользователя на конкретную правку.

Общую часть с akit (разбор транскриптов, процесс → сессия, давление машины) брать из библиотеки akit, а не копировать: у «процесс → сессия» сейчас пять копий.

## Два вида контроля
1. **Границы одного агента.** Чтобы один агент не отъел память, диск или процессор у всех, и чтобы его действия не выходили за его дерево: чужие проекты, `/tmp`, порты, контейнеры. Нарушение получает сам агент: «твой `route.test` занял 12 ГБ».
2. **Хватает ли ресурса вообще.** Запас и его тренд («диск кончится через 9 дней при нынешнем росте»). Сигнал лиду; пользователю — только когда нужно физическое действие. Сигналы сторожей — письмом сессиям; Telegram-группа Дайджеста — не их канал (пользователь 28.10 11:58 CET на сигналы сторожа ночи там: «не надо так»), другой канал к пользователю — только с его «да». Сигнал о самом лиде (ночь не стартовала) уходит и запасному адресату, `night.also_to`, по умолчанию git-admin.

Главная мера — **ожидания и отказы**, а не только гигабайты. Больнее всего агенту время простоя: в очереди, без лимита, без входа, без PC. Это механизм для принципа пользователя «Видишь очередь - разберись в причинах» (25.10, `~/.claude/CLAUDE.md`).

## Устройство
- Один конфиг `~/.config/aguard/config.toml` (пример — `deploy/config.example.toml`): общие `lead`, `send_auth`, `[admins]` и разделы наблюдателей `[orphans]`, `[tmp]`, `[memory]`, `[restart]`, `[waits]`, `[compact]`, `[disk]`, `[said]`, `[bgtask]`, `[cpu]`, `[io]`. Неизвестный ключ — ошибка: опечатка не должна молча включать умолчание. `[admins]` в файле заменяет список по умолчанию, а не дополняет. Демон перечитывает конфиг каждый проход; не прочитался — проход пропускается, по неизвестным правилам ничего не делаем.
- Наблюдатели демона — `orphans` (бывший procguard), `tmp` (бывший tmpguard), `memory`, `waits`, `agentwaits`, `compact`, `disk`, `said`, `bgtask`, `cpu`, `io`; у каждого свой интервал, паника одного не роняет остальных. Состояние — `~/.local/state/aguard/<наблюдатель>/`.
- tmpguard-track остаётся отдельной root-службой (fanotify и proc connector требуют root); aguard читает его снимок из `/run/tmpguard` и `/var/lib/tmpguard`.
- `memory` раз в минуту читает cgroup каждой сессии (`agents.slice/agent-<имя>-<pid cl>.scope`): `memory.peak` с ядра 6.12 сбрасывается записью в свой открытый файл, поэтому каждая запись — пик за прошедший интервал. Память cgroup включает файловый кеш — её же считает `MemoryHigh`, так что порог выбирается по той же мере. Первая запись scope несёт пик за всю жизнь сессии до aguard и в отчёте идёт отдельным столбцом. Записи — дневные JSONL в `~/.local/state/aguard/memory/`, прошлые дни сжимаются, хранятся 60 дней. Отчёт по ролям — `aguard memory report`.
- `restart` — решение «можно ли перезапустить сессию» (бывший `decide.go` cl с его фактами: реестр, chooks, транскрипт, терминал, дети процесса). Интерфейс принял git-admin, владелец cl, 25.10: cl на каждом тике шлёт в сокет `$XDG_RUNTIME_DIR/aguard/aguard.sock` строку JSON `{v, pid, name, args_problem, typed}` и ждёт около 2 с ответ `{v, restart, fresh, against, key, mode, session_id, name, running, installed, crons, recreate, compact, compact_against, compact_key, tokens}`. Нет ответа, другая версия протокола или `error` — cl не перезапускает и не сжимает. Аргументы запуска знает только cl, поэтому `args_problem` считает он сам; его флаги сессии (обход cc-cwd-reset) тоже остаются в cl. `crons` — у сессии есть таймеры. После `/clear` и сжатия Claude Code пишет attachment `session_cron_carry`: `tasks` — таймеры своей беседы, `otherArmed` — унаследованные из прошлой. `--resume` возвращает свои таймеры из `CronCreate` и `tasks`, но теряет `otherArmed`. При унаследованных aguard запрещает перезапуск; если все выражения cron известны и cl работает под pty в режиме `act`, он набирает команды `CronCreate`, затем агент удаляет прежние таймеры. После подтверждения, что они стали своими, следующий проход разрешит обычный перезапуск. Ручной вопрос — `aguard restart ask -pid N`; `-claude` подставляет другую ссылку на установленный claude, чтобы проверить решение «как при новой версии».
- Черновик в поле ввода — по экрану терминала (`internal/screen`), и для перезапуска, и для сжатия. Время ввода в терминал (atime pts) черновик не ловит, если текст набран во время хода: ввод старше конца хода. Проверено 25.10 на пробной сессии в tmux: черновик набран в 17:06:16 CET, ход кончился позже, и в 17:18 aguard без проверки экрана ответил `restart: true`. Экран: процесс внутри tmux (`TMUX` в окружении) — `tmux capture-pane` его панели; иначе вкладка konsole из предков процесса — D-Bus `org.kde.konsole-<pid>`, `/Sessions/N`, вкладка с тем же терминалом, `getAllDisplayedTextList`. Чтение экрана Konsole открыто без настроек. Поле — рамка: верхняя линия из «─» (справа бывает имя сессии), строка «❯ …» с продолжениями, нижняя линия, под ней не больше 8 строк статуса. Пусто — только при одних пробелах внутри рамки; рамки не видно (диалог, прокрутка, длинное меню), экран не прочитался или терминал не Konsole и не tmux — против. Серый образец новой сессии `Try "…"` по тексту неотличим от набранного и считается черновиком. Проверка по времени ввода (`draft`) держит, только если экран не подтвердил пустое поле (решение пользователя 26.10 20:54 CET, вариант 2 из трёх). Ввод после конца хода при пустом поле — обычно байты фокуса, не человек: Claude Code включает отчёт о фокусе (`ESC[?1004h`), и Konsole при переключении на вкладку шлёт его в терминал, сдвигая atime pts. Раньше `draft` держал и при пустом поле, и тогда любая вкладка, на которую переключились после конца хода, не сжималась до следующего хода. Человека у вкладки по-прежнему бережёт `tty`: ввод за последние 2 мин для сжатия и за 10 мин для перезапуска. Серая подсказка следующей реплики Claude Code (prompt suggestion) по тексту тоже неотличима; пользователь её не выключает (30.10: «агенты работают автономно, я в консоль ничего не пишу, их подсказка сходит с ума. Но иногда всё же полезна»). Отличает cl под pty: он видит весь ввод человека (`cmd/cl/draft.go`). Знаки, Tab, история и вставка — текст; Enter, Ctrl+C, запуск claude и набор cl — поле чистое; фокус, ответы терминала и мышь поле не меняют. Чистое поле cl шлёт как `clean`, и тогда текст на экране — подсказка, а `draft` по atime не нужен. Прежний признак по atime раньше реплики typed остался для сессий без cl. Поле, о котором cl не знает (подхват на ходу от прежнего cl), чистеет, когда aguard увидит его пустым (`field_empty`, во время любого хода), а человек с вопроса ничего не вводил.
- `compact` — своё сжатие бесед в простое (задача лида и пользователя 25.10 16:51 CET: порог 100 тыс., встроенное сжатие Anthropic выключить, «раз у них не всегда вовремя срабатывает»). Кэш подсказки живёт час от начала запроса. Беседа, брошенная с большим контекстом, после часа пишет весь контекст в кэш заново. Сжатие до конца часа читает контекст из живого кэша, и следующий запрос идёт уже от короткой сводки. Раз в минуту по каждой живой интерактивной сессии реестра: последний запрос основной ветки транскрипта (начало — реплика или результат инструмента перед ответом, контекст — вход, кэш и выход ответа), сжатие после него (`compact_boundary`) и те же проверки свободы, что у перезапуска: ход закончен (`idle`, chooks `done`/`waiting`), нет детей, идущих инструментов, фоновых задач и суб-агентов, поле ввода пустое по экрану и по времени ввода, ввод в терминал не меньше 2 минут назад. Версия и порог простоя перезапуска не нужны. Окно — 53–57 минут от начала запроса: встроенное срабатывает около 54-й, а позже 57-й кэш может умереть раньше, чем сжатие его прочитает. Разбор транскрипта общий с `restart`: дочитывается с конца разобранного, а не перечитывается.
- `compact` в режиме `log` пишет одно решение на запрос: `would` (сжал бы) или `would_not` с кодами доводов против. Потом сверяет решение с тем, что случилось: `compacted` (сжали — встроенное в простое, автосжатие или человек; с trigger), `cache_alive` (следующий запрос прочитал из кэша не меньше половины контекста — человек вернулся при живом кэше), `cache_expired` (кэш умер, сжатие сэкономило бы), `lost` (сессия пропала на неделю). Журнал — `~/.local/state/aguard/compact/<день>.jsonl`, решения без исхода — `state.json` там же. Сводка — `aguard compact report`; `-json -at <RFC3339>` — для sleepstats и страницы Сна, формат версии 1: `{v, at, windows: {day, week, month}}`, в каждом окне решения, доводы против, исходы с числом и суммой контекста и нечитаемые строки. Решение пишется в момент входа в окно, а cl действует по ответу на каждый свой опрос — позже условия бывают другими. Поэтому в сводке рядом и то, что cl сделал на деле по своему журналу `~/.local/state/cl/restart.log` (формат строк и разбор — `internal/cllog`, один на cl и aguard): `done` — по «вид/итог» (`compact`, `reset`, `type_compact`, `type_clear` × `done`, `failed`, `skipped`, `stopped`, `none`), `sessions` — по сессии решения aguard и сделанное cl (поля добавлены в версию 1, прежние не менялись). Режим `act` — в cl (ниже).
- `compact` пишет и «сбросил бы» (`/clear`): задача лида 25.10 по реплике пользователя 18:14 CET о сессии с закрытой работой и подсказкой Claude Code «new task? /clear to save 235.7k tokens» — «ну вот в таком случае, например, я бы сбрасывал сессию» (транскрипт лида `~/.claude/projects/-home-alice/0bbcc980-299c-4952-9456-a5d0841affb0.jsonl`). Сбрасывает cl по полю `reset` в ответе (режим `reset_mode` в его конфиге, по умолчанию log): останавливает claude и поднимает новую беседу с теми же флагами, строкой роли и файлом возобновления — тем же путём, что сжатие через перезапуск. В терминал никто не печатает: ввод в сессию агента — через cl по сообщению aguard (пользователь 25.10 17:49 CET в сессии git-admin: «Пускай отправляет сообщение cl, а тот уже пишет»); задание Сна 26.10 — 25.10 18:26 пользователь сам набирал `/clear` у akit, потому что cl умел только продолжать ту же беседу. Сброс по умолчанию, сжатие — только где сброс нельзя (пользователь 27.10 10:48 CET в транскрипте лида `8d06de04`: «мы должны использовать сброс везде где можем. Компакт это компромисс»; вариант 3 лида — 11:12 CET «Да, давай 3»; до того за 7 дней было «сжал бы» 24 и «сбросил бы» 1 из 554: сжатие в 53–57 мин всегда шло раньше сброса от часа, после него держал довод `compacted`, а без подсказки — `hint`). Условия: контекст от `min_tokens` и последний запрос не ближе `after`, как у сжатия, без верхней границы окна (кэш новой беседе не нужен); прошлое сжатие сброс не держит; те же проверки свободы, что у сжатия (и аргументы запуска восстановимы); таймеров нет вовсе (сброс их не восстановит); чистое git-дерево папки сессии (`git status` — только когда остальное за). Где сброс можно, сжатие получает довод `reset` (`preferReset`). Подсказку Claude Code «/clear to save» aguard больше не читает. Итог хода («закрыты», «ничего не жду», «следующее — <дата>») условием не стал — фразы разные; он пишется в запись (`reply`) для сверки. Запись решения — с моделью, контекстом и ценой: `rewrite_micro_usd` — следующий запрос после смерти кэша пишет контекст заново (запись на час — 2× входа), `read_micro_usd` — каждый запрос при живом кэше; цены — по справке claude-api (`internal/compact/price.go`), это оценка. Исходы — общие со сжатием плюс `cleared`: у процесса сессии новая беседа, человек сбросил сам. При новом запросе в исход пишется реплика человека (`prompt`): по ней видно, нужен ли был старый контекст. В `report -json` (формат v1, поля добавлены) — решения `would_reset`/`would_not_reset`, `held` (по решению: число, контекст, `micro_usd`), `reset_against`, у исходов — `micro_usd`; деньги — в миллионных долях доллара целым числом.
